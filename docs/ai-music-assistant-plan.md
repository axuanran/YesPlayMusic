# XuMP AI 音乐助手：技术方案与实施计划

> 目标：把 XuMP 从"播放器 + MCP 控制面"演进为**用户能调教的私人音乐助手**。
> 核心原则：**大模型理解需求，程序约束和执行**；模型不可用时普通播放完全不受影响；
> 推荐理由必须来自真实标签/音频分析/可核验数据，不允许编造。

## 0. 现状盘点（代码库事实）

已有的可复用资产：

- **控制面**：`src/electron/controlHandlers.js` 提供 `status / control / play / enqueue / queue / search / lyrics / recommend / like`；
  MCP 双通道（Streamable HTTP + stdio）已可用，具备事件推送能力（`desktop-lyrics:settings-changed` 等已有先例）。
- **歌词数据**：`lyrics` 接口按毫秒返回时间戳歌词（翻译/发音都有）；歌词页已有单句循环（Alt+E）、桌面歌词多行模式。
- **播放内核**：Player 支持 seek / repeatMode / shuffle / playNextList 优先队列；`xumpctl` CLI 可脚本化验证。
- **曲库来源**：网易云（搜索/推荐/喜欢）、本地音乐扫描、Emby/Jellyfin 流媒体——多源统一队列已存在。
- **持久化模式**：渲染层 localStorage 插件 + 主进程 electron-store 镜像（settings 双向链路刚补齐）；
  样式导出/导入（version 2 + DPI/位置）可直接复用为"配方/偏好"的分享格式。
- **队列能力缺口**（Phase 0 要补）：queue 目前只读 + 追加，**无重排/替换/清空**；无反馈事件；
  无偏好记忆；无"请求已接受 vs 实际在播"之外的状态机扩展。

## 1. 总体架构

```
┌────────────────────────────────────────────────────────────┐
│ 表现层（Vue）                                               │
│  电台反馈条 · 偏好面板 · 歌词伴读卡片 · 配方编辑器 · 探索转盘 │
└──────────────┬─────────────────────────────────────────────┘
               │ IPC / MCP
┌──────────────▼─────────────────────────────────────────────┐
│ 助手核心（主进程，新增 src/electron/assistant/）            │
│  PreferenceStore   三层偏好（会话/临时/长期）持久化          │
│  FeedbackBus       播放事件流（skip/complete/like/radio）    │
│  RadioEngine       候选生成→打分→LLM 选择→程序校验→队列续杯  │
│  RecipeEngine      配方解析→确定性调度→中途重规划            │
│  LyricTutor        伴读卡片生成（解释/例句/事实分离）        │
│  LLMClient         OpenAI 兼容接口，可配置本地/远端          │
└──────────────┬─────────────────────────────────────────────┘
               │
┌──────────────▼─────────────────────────────────────────────┐
│ 执行层（现有）：Player / controlHandlers / 缓存 / Resolver  │
└────────────────────────────────────────────────────────────┘
```

关键约束：

- LLM 只输出**候选与理由**，程序负责校验存在性、版本、时长、可播放性后才入队；
- 偏好数据**仅存本地**（electron-store），不上传；
- 每个 AI 决策可解释：记录"这条规则来自哪次反馈"，用户可见、可改、可删。

## 1.5 Phase 1.5 — 音轨情报与候选池（P1.5，地基扩展）

**目标**：让"听过的歌"沉淀为结构化情报，让候选池可被人为/AI 扩充，使偏好规则
有结构化抓手（而不是只能靠 LLM 从歌名里猜）。

1. **音轨情报库**（主进程 `assistant/trackIntel.js`，electron-store `assistantTracks`，
   上限 2000 条）：`{id(带命名空间 ne:/local:/emby:), name, artists, album, durationMs,
   source, heard:{count,lastAt,completedCount,skipQuickCount}, liked, added:{at,by},
   derived:{tags[], mood, isLive, enrichedAt, audio?}}`。
2. **heard 管线**：Player 的 complete/skip/like 信号 → `recordHeard` 累加计数；
   LLM 富化（元数据 + 歌词片段 → 受控 JSON：tags/mood/isLive）→ `setDerived`；
   音频特征（tempo/energy，offlineAudioContext 提取，opt-in）为 P4"片段找歌"预留字段。
3. **候选池**：每日推荐 ∪ 情报库（听过/人工/AI 加入）→ `buildCandidatePool()`；
   `pool.expand` 支持 `{ids}` 人工加入与 `{keywords}` AI 扩源（LLM 按规则/上下文生成
   搜索词 → 搜索 API → 入库 by:'ai'）。
4. **结构化预过滤**：派生字段 + 歌名启发式（现场/Live/演唱会）→ 命中"不要现场版"
   类规则时程序硬过滤，LLM 只处理剩余语义。
5. MCP 工具 `music_pool`（list / add / seek）；电台候选源切换到候选池。

**消费顺序**：电台选歌（现在）→ AI 找歌相似度（P4）→ 歌词伴读上下文（P2）。

## 2. Phase 0 — 控制面补齐（1 周，后续一切的地基）

**目标**：让外部/内部 Agent 能完整操纵队列并收到反馈。

1. `control` 扩展：`replaceQueue / reorderQueue / clearQueue / moveTrack`（复用现有 `handleMprisCommand` 白名单模式，逐条加校验）。
2. **反馈事件总线**：Player 已有 skip/complete 语义点，新增 `FeedbackBus` 发 `player:feedback`
   （`{type: skip|complete|like|unlike|seek_away, trackId, at, context}`），MCP 客户端可订阅，
   助手核心内部消费。
3. **偏好存储**：`assistant/preferences.json`（electron-store 命名空间）：
   ```json
   {
     "longTerm": [{ "rule": "...", "source": "explicit|inferred", "scope": "global|context:<id>",
                    "confidence": 0.9, "createdAt": 0, "updatedAt": 0 }],
     "temporary": [{ "rule": "...", "expiresAt": 0, "reason": "用户反馈：最近听腻了" }],
     "session":   [{ "rule": "...", "sessionId": "..." }]
   }
   ```
4. MCP 新工具：`feedback`（自然语言反馈 + 结构化信号）、`preferences.get/patch`、
   `radio.start/adjust/stop` 占位（Phase 1 填实现）。
5. 测试：queue 操作单测、FeedbackBus 事件契约、偏好存储归一化。

## 3. Phase 1 — 可调教的私人电台（3–4 周，**第一优先**）

**产品闭环**：说一句话 → 看懂三层语义 → 调整后续队列 → 用户看得见改了什么。

1. **反馈管线**：
   - 显式入口：播放条快捷语（"继续这种感觉，少点慢歌"）、歌词页右键、MCP `feedback`；
   - 弱信号：30 秒内切走记一次 `skip_quick`，连续 3 次才生成"暂时降权"候选规则（需用户确认才转正）；
   - LLM 只做语义分层（本次/暂时/长期），输出受控 JSON，程序落库。
2. **RadioEngine**：
   - 候选源：网易云 `recommend/search` + 本地曲库扫描 + 流媒体目录（各源已有访问层）；
   - 确定性预过滤：长期规则硬过滤（"不要现场版"）、临时规则降权、同歌手间隔、N 日内不重复；
   - LLM 在 20–50 个候选中选 5–10 首并给理由（候选必须来自检索结果，禁止凭空生成 ID）；
   - **队列续杯**：播到队列剩 3 首时异步补货；当前曲永不打断。
3. **偏好面板**（设置页新分区）：每条规则显示 内容/来源/适用范围/操作（改、删、升级为长期）；
   "你在专注模式下倾向纯音乐"这类推断必须标注来源并可一键否定。
4. **"为什么播这首"**：每首 AI 入队曲目带一句真实理由（来自命中的规则或候选标签）。
5. 降级：LLM 不可用时退化为纯规则引擎（只用偏好过滤 + 推荐接口），电台仍可用。

里程碑：M1 反馈闭环可用（第 2 周末）；M2 电台连续播放 1 小时无人工干预可教（第 4 周）。

## 4. Phase 2 — AI 歌词伴读（2 周，**最易演示**）

范围收窄为"选中一句 → 解释 → 循环 → 收藏复习"完整小循环：

1. 歌词页每行加"伴读"入口（复用现有右键菜单位）；卡片展示：字面意思 / 语境解释 / 值得学的表达 / 日常例句。
2. **解释与事实分离**：语言分析走 LLM；创作背景/歌手经历只展示有可核验来源的内容，无来源则明确标注"未经证实"。
3. 收藏进"学习集"（本地表：歌曲/时间点/表达/例句），可从学习集一键跳回歌曲并调用已有单句循环。
4. "我听不清这里"→ 复用 `seekTo + repeatLyricLine`（链路已存在）。
5. MCP：`lyrics.explain` 工具（同卡片的同款输出，AI 客户端可用）。

## 5. Phase 3 — 听歌配方（2–3 周）

1. 配方 = 一份可见的 YAML/JSON 规则文档（时长弧线、熟悉度比例、同歌手间隔、近 N 日排除、
   上下文约束）——复用样式导出 v2 的格式经验做导入/导出与分享。
2. 确定性调度器生成候选曲线（开始轻松→中间有节奏→结尾安静），LLM 只负责选曲与微调；
3. **中途调整**："后面保持现状"→ 只重排剩余段，不打断当前曲；
4. 朋友导入配方时基于**自己的曲库**执行——分享的是方法不是歌单。

## 6. Phase 4 — "我喜欢的是这一段"（4–6 周，**标志性实验**）

1. **先本地、先 opt-in**：仅对用户勾选"允许分析"的本地音乐建索引；
2. 导入/后台任务抽取片段 embedding（CLAP 类模型，ONNX 侧车进程，GPU 可选）；
   向量存 sqlite-vec/ Lance，按 `trackId + 时间段` 存；
3. UI：进度条拖选片段 → "用这段找歌" → 返回候选**片段**（带各自起点偏移，试听直接 seek 到对应段）；
4. 收藏对象扩展为"声音片段"（我喜欢的鼓点/前奏/人声库）；
5. **先验证再扩面**：内部 20 人盲测"真的像吗"，通过后才考虑在线音源与细粒度维度（只像贝斯/只像人声）。
   效果不达标就诚实收窄为"整曲听感相似"。

## 7. Phase 5 — 多源管家 & 探索向导（3 周）

- 虚拟整理层：智能标签、收藏关系、重复/替代版本**建议**（不自动改文件/元数据）；
- "收藏但很久没听"复活清单；版本偏好显式化（"喜欢这个版本"）；
- 探索向导：熟悉度滑杆（←接近口味 →更大胆），每步只解释一个真实联系（标签/音频相似/可靠资料），可回退一层。

## 8. Phase 6 — 多人 AI DJ（2 周，后续扩展）

房间制：每人只给"几首喜欢的歌 + 此刻想要的感觉 + 禁区"。**公平轮换/重复限制用确定性规则**，
LLM 只做偏好协调与一句话说明；不暴露成员完整听歌历史。

## 9. 横切事项

| 事项 | 方案 |
|---|---|
| LLM 接入 | OpenAI 兼容客户端，设置页配置 baseURL/key；支持 ollama 等本地后端；所有调用可关闭 |
| 测试 | 规则引擎/偏好存储单测；RadioEngine 用 fake LLM 做集成测试；xumpctl 脚本做 E2E 回归 |
| 隐私 | 偏好与片段索引全部本地；音频分析显式 opt-in；日志不落歌词内容 |
| 失败模式 | LLM 超时→重试一次→降级规则引擎；队列操作幂等；事件至少一次 |

## 10. 优先级与人力估算

| 阶段 | 内容 | 建议顺序 | 粗略工时 |
|---|---|---|---|
| P0 | 控制面补齐 | **立即** | 1 周 |
| P1 | 可调教私人电台 | **第一优先** | 3–4 周 |
| P2 | AI 歌词伴读 | 与 P1 后半并行 | 2 周 |
| P3 | 听歌配方 | P1 之后 | 2–3 周 |
| P4 | 片段找歌 | 标志性实验，验证驱动 | 4–6 周 |
| P5 | 多源管家/探索向导 | 长期打磨 | 3 周 |
| P6 | 多人 DJ | 场景扩展 | 2 周 |

**如果只做一个：P1（可调教的私人电台）**——它直接建立在刚补齐的 MCP/设置链路上，最快形成
"AI 真正参与日常听歌"的体感；**如果做一个标志性实验：P4**，但务必按"先本地、先验证"的收窄路径走。
